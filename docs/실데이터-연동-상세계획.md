# 국내증시 MVP 실데이터 연동 상세 계획

작성일: 2026-04-24  
대상 저장소: `d:\git\auto-project`

## 1. 문서 목적

이 문서는 현재 실데이터 저장소를 전제로 동작하도록 정리된 국내증시 MVP에 실제 데이터 파이프라인을 붙이기 위한 상세 구현 계획서다.

목표는 다음 3가지다.

1. `장마감 이후 EOD 배치` 기준으로 실제 종목 후보를 생성할 수 있을 것
2. `점수 + 선정 이유 + 위험 신호`를 실제 데이터로 설명 가능하게 만들 것
3. 현재 코드 구조를 최대한 유지하면서 `샘플 저장소 -> 실데이터 저장소`로 자연스럽게 교체할 것

## 2. 현재 상태 요약

현재 시스템은 아래 상태다.

- FastAPI 서버와 검색 가능한 웹/모바일 겸용 대시보드가 존재
- 점수 엔진과 후보 선정 규칙은 구현 완료
- 실데이터가 없으면 후보가 비어 있는 상태로 동작
- 외부 시세, 공시, 뉴스, 시장경보, DB 영속화는 아직 미연결

즉, `서비스 동작 흐름은 완성`, `데이터 공급망은 미완성` 상태다.

## 3. 핵심 제약과 전제

### 3.1 MVP가 만족해야 하는 운영 조건

- 대상 시장: KOSPI / KOSDAQ
- 장마감 이후 배치 실행 시각: `15:50 KST 이후`
- 사용자 노출 시점: `다음 거래일 장 시작 전`
- 평가 구간: `1~3거래일 단기 모멘텀`
- 점수 방식: `룰 + 가중치`
- 실시간 자동매매 없음

### 3.2 데이터 소스 선택의 현실적 제약

실제 운영 시 가장 중요한 제약은 `당일 장마감 직후 데이터 확보 가능 여부`다.

공공데이터포털의 `KRX상장종목정보`, `주식시세정보`는 공식 설명상 기준일 다음 영업일 오후 1시 이후 반영될 수 있으므로, 설계서의 `당일 EOD 배치` 목표에 그대로 쓰기 어렵다. 따라서 다음과 같이 분리해야 한다.

- `당일 EOD 배치용 시세`: 증권사 Open API
- `유니버스 마스터 / 보조 백필`: 공공데이터포털
- `공시`: Open DART
- `시장경보`: KIND 또는 별도 공급원

## 4. 추천 데이터 소스 구성

### 4.1 1차 권장 구성

#### A. 시세/거래량/거래대금

- 권장: 한국투자 Open API
- 역할:
  - 종목 마스터 보조
  - 장마감 기준 종가, 고가, 저가, 거래량, 거래대금
  - 필요 시 분봉/현재가 확장 가능
- 이유:
  - 당일 시세 확보 가능
  - 공식 문서와 인증 절차가 명확
  - 향후 실시간 확장 여지 존재

#### B. 공시/이벤트

- 권장: Open DART
- 역할:
  - 종목 코드와 DART 고유번호 매핑
  - 공시 검색
  - 원문 링크 제공
  - 촉매 스코어용 이벤트 분류
- 이유:
  - 공식 공시 소스
  - 설명 가능한 이유 생성에 적합

#### C. 상장종목 마스터

- 권장: 공공데이터포털 `KRX상장종목정보`
- 역할:
  - 단축코드, 종목명, 시장구분, ISIN, 법인 정보 확보
  - 유니버스 기초 마스터 관리
- 이유:
  - 일일 동기화에 적합
  - 무료

#### D. 보조 EOD 검증 / 백필

- 권장: 공공데이터포털 `주식시세정보`
- 역할:
  - 익일 검증
  - 데이터 정합성 비교
  - 백테스트 리플레이용 보조 소스
- 이유:
  - 무료
  - 필드가 풍부
- 주의:
  - 당일 장마감 직후 배치 소스로는 부적합

#### E. 시장경보/거래정지/관리종목

- 권장: KIND 기반 수집 커넥터
- 역할:
  - 투자주의/경고/위험
  - 거래정지
  - 관리종목 상태
- 주의:
  - 공식 공개 OpenAPI 문서를 즉시 확정하기 어려우므로 초기엔 수집 커넥터를 별도 레이어로 두고 공급원 교체가 가능해야 함

#### F. 뉴스/RSS

- 권장: 신뢰 가능한 경제지 RSS 또는 공식 뉴스 API
- 역할:
  - 정책/업황/계약/실적 관련 텍스트 촉매 보강
- 주의:
  - 풍문성 기사 필터링 필요
  - 초기에 뉴스는 가중치를 공시보다 낮게 두는 것이 안전

### 4.2 최종 권장 조합

- 시세: 한국투자 Open API
- 공시: Open DART
- 상장종목 마스터: 공공데이터포털 KRX상장종목정보
- EOD 백필/검증: 공공데이터포털 주식시세정보
- 시장경보: KIND 커넥터
- 뉴스: 신뢰 가능한 뉴스/RSS 커넥터

## 5. 소스별 책임 분리 원칙

데이터 소스는 반드시 책임을 분리해야 한다.

- 브로커 API는 `장마감 직후 시세`
- DART는 `공시와 공식 이벤트`
- 공공데이터포털은 `마스터/검증/백필`
- KIND는 `리스크 상태`
- 뉴스는 `보조 촉매`

하나의 API에 모든 책임을 몰아주면 장애 시 전체 배치가 멈춘다.

## 10. 수집기별 상세 설계

### 10.1 master_data_collector

목표:
- 상장종목 전체 마스터 구축

입력:
- 공공데이터포털 `KRX상장종목정보`

출력:
- `stock_master`

처리 규칙:
- 신규 종목 upsert
- 상장폐지/비활성 종목 상태 갱신
- 보통주 여부 파생 컬럼 생성
- ETF/ETN/우선주/SPAC 분류 규칙 적용

주의:
- 종목명 suffix만으로 우선주를 판정하면 오탐이 발생할 수 있으므로 보조 규칙 필요

### 10.2 market_data_collector

목표:
- 당일 장마감 직후 종목별 EOD 스냅샷 수집

입력:
- 브로커 Open API

출력:
- `daily_prices`

필수 필드:
- 종가
- 고가
- 저가
- 시가
- 거래량
- 거래대금

추가 계산은 저장 후 서비스 레이어에서 수행한다.

수집 전략:
- 유니버스 전체를 분할 호출
- 실패 시 재시도
- 부분 실패 허용

운영 포인트:
- API 호출 제한에 맞춰 배치 큐 구성
- 종목 마스터와 코드 체계를 일치시킬 것

### 10.3 disclosure_collector

목표:
- DART 공시를 촉매용 구조 데이터로 변환

입력:
- Open DART `고유번호`
- Open DART `공시검색`
- 필요 시 원문 링크

출력:
- `daily_disclosures`

처리 규칙:
- `code -> dart_corp_code` 매핑 캐시 유지
- 보고서명 기반 rule tagging
  - 실적
  - 공급계약
  - 신규사업
  - 투자/취득
  - 정책 수혜 관련 공시
- 동일 공시 중복 적재 방지

가중치 원칙:
- 공시 기반 이벤트는 뉴스보다 높은 신뢰도

### 10.4 warning_collector

목표:
- 배치 리스크 패널티용 상태 확보

입력:
- KIND 또는 대체 공급원

출력:
- `daily_market_warnings`

처리 규칙:
- 투자주의/경고/위험 정규화
- 거래정지 여부 정규화
- 관리종목 여부 정규화
- 장 종료 시점 기준 상태 우선

주의:
- 이 레이어는 공급원 변경 가능성을 고려해 인터페이스 기반으로 설계

### 10.5 news_collector

목표:
- 설명 가능한 보조 촉매 확보

입력:
- 신뢰 가능한 뉴스/RSS

출력:
- `daily_news`

처리 규칙:
- 중복 기사 제거
- 종목명/코드 기반 매핑
- 신뢰도 점수 부여
- 풍문성/재전송/광고성 기사 필터링

주의:
- 초기 MVP에서는 뉴스가 전체 점수를 과도하게 흔들지 않도록 상한 제한 필요

## 11. 정규화 계층 설계

실데이터에서 가장 많이 깨지는 부분은 `코드/종목명/법인명 매핑`이다.

반드시 아래 유틸을 둬야 한다.

### 11.1 SymbolMapper

역할:
- `stock code`
- `dart corp code`
- `isin`
- `corp_name`
를 서로 변환

### 11.2 SectorMapper

역할:
- 섹터명이 소스별로 다를 때 내부 공통 섹터명으로 정규화

예:
- `반도체`
- `Semiconductor`
- `반도체 및 관련장비`
를 하나의 내부 분류로 통합

### 11.3 EventClassifier

역할:
- 공시/뉴스 제목을 내부 촉매 카테고리로 분류

예:
- `계약`
- `실적`
- `정책`
- `임상`
- `업황`

### 11.4 WarningNormalizer

역할:
- 여러 경보 문자열을 내부 표준 상태로 통합

예:
- `attention`
- `warning`
- `danger`
- `halted`
- `managed`

## 12. 배치 파이프라인 상세

### 12.1 일일 실행 흐름

1. `15:50 KST` 이후 배치 시작
2. 상장종목 마스터 유효성 확인
3. 당일 시세 수집
4. 당일 공시 수집
5. 당일 뉴스 수집
6. 당일 시장경보 수집
7. 종목별 스냅샷 조립
8. 피처 계산
9. 점수 계산
10. 섹터 컷오프 및 Top 10 선정
11. DB 저장
12. API와 대시보드에 반영

### 12.2 실패 허용 원칙

배치는 일부 데이터 소스 장애가 있어도 전체가 중단되지 않아야 한다.

예:
- 뉴스 실패 -> 뉴스 피처만 `null`
- DART 실패 -> 공시 스코어 `0`, 원인 로그 기록
- 시장경보 실패 -> 리스크 배지에 `미확인` 표시 가능

### 12.3 재실행 정책

- 동일 일자 배치를 재실행할 수 있어야 함
- `generated_at` 최신값 기준으로 overwrite 또는 version 관리
- 운영 초기에는 overwrite가 단순하고 유리

## 13. 스냅샷 조립 규칙

`StockSnapshot`는 단일 소스에서 만들지 말고 조합해서 만들어야 한다.

입력 조합:

- `stock_master`
- `daily_prices`
- `daily_disclosures`
- `daily_news`
- `daily_market_warnings`
- 과거 20일 가격/거래량 이력

스냅샷 생성 시 계산 항목:

- 최근 20일 평균 거래대금
- 최근 20일 평균 거래량
- 거래대금 배수
- 거래량 배수

- 종가 위치
- 윗꼬리 비율
- 갭상승률

- 섹터 거래대금 배수

## 14. 점수 엔진 실데이터 연결 시 수정 포인트

현재 `app/scoring.py`는 구조상 유지 가능하다.

다만 아래는 실데이터 연결 시 보강해야 한다.

### 14.1 유니버스 제외 규칙 강화

- 보통주/우선주 판별 정확도
- SPAC 판별 정확도
- 거래정지/관리종목 최신성
- 상장일 계산 정확도

### 14.2 촉매 점수 보강

- DART 보고서명 사전
- 뉴스 발행처 신뢰도 사전
- 동일 이벤트 중복 가점 방지

### 14.3 섹터 동조성 보강

- 섹터 정의 테이블 필요
- 섹터별 상위 동반 상승 종목 계산 로직 필요

## 15. API 변경 계획

현재 API 스펙은 유지하되 내부 구현만 바꾸는 것이 좋다.

### 15.1 그대로 유지 가능한 API

- `GET /api/candidates/daily`
- `GET /api/stocks/{code}/signal-summary`
- `GET /api/backtests/summary`
- `GET /api/stocks/search`

### 15.2 내부 변경 포인트

- 샘플 데이터 제거 후 PostgreSQL 저장소로 일원화
- DB 기반 Repository로 교체
- 검색 엔드포인트는 `stock_master + daily_candidate_scores` 조인 조회

범위:

- PostgreSQL 도입

## 23. 결론

이 프로젝트는 현재 구조를 버릴 필요가 없다.

가장 좋은 전략은 아래다.

1. `샘플 저장소`를 바로 지우지 않는다.
2. `실데이터 repository`를 병렬 추가한다.
3. 배치가 안정화되면 PostgreSQL 저장소를 기본 경로로 유지한다.
4. 마지막에 UI는 그대로 두고 데이터 공급만 실데이터로 전환한다.

즉, 다음 구현의 본질은 `새 프론트 개발`이 아니라 `실데이터 파이프라인 구축`이다.
