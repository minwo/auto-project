# 📂 프로젝트 구조 분석 및 개선 사항 리포트

> 작성일: 2026-05-04
> 목적: 현재 `auto-project`의 폴더 구조와 코드 베이스를 분석하고 향후 유지보수성 및 확장성을 높이기 위한 구조적 개선 사항을 도출합니다.

---

## 1. 현재 폴더 구조 및 현황 파악

현재 프로젝트는 다음과 같은 구조를 가지고 있습니다.
- `app/`: FastAPI 기반의 백엔드 시스템 및 도메인 핵심 로직, 스크립트(`scripts/`), 수집기(`collectors/`) 혼재
- `frontend/`: Next.js(App Router) 기반의 프론트엔드
- `sql/`: 데이터베이스 스키마 정의 (`schema.sql`)
- `docs/`: 기획 및 설계 문서
- `tests/`: pytest 기반의 백엔드 테스트 코드

### 1.1 백엔드 (`app/`)
- `main.py` 파일 하나에 모든 API 엔드포인트(라우터)와 비즈니스 로직이 집중되어 있어 파일이 거대해지고 있습니다(300줄 이상).
- 도메인(`domain.py`), 스코어링 로직(`scoring.py`, `surge_scoring.py`), 데이터베이스 접근(`repository.py`, `postgres_repository.py`)이 루트에 모두 흩어져 있어 **Layered Architecture(계층형 구조)** 분리가 부족합니다.

### 1.2 프론트엔드 (`frontend/`)
- `app/page.tsx` 파일이 약 **1,200줄(41KB)** 에 달하는 거대한 Monolith 형태입니다.
- API 호출 로직, 전역 상태 관리, UI 컴포넌트(`MarketRegimeBanner`, `SignalDetail` 등), 타입 정의가 하나의 파일에 묶여 있어 가독성과 재사용성이 매우 떨어집니다.

### 1.3 인프라 및 배포
- `docker-compose.postgres.yml`을 통해 DB 환경만 제공되고 있으며, 백엔드와 프론트엔드 앱 자체를 구동하기 위한 `Dockerfile`이나 전체 통합 `docker-compose.yml`이 부재합니다.

## 2. 주요 개선 사항 (Action Items)

### 🎯 1. 백엔드(FastAPI) 계층형 아키텍처 분리
현재 평면적인 구조를 역할별 디렉터리로 분리하여 결합도를 낮추어야 합니다.

**권장 구조:**
```text
app/
 ├── api/           # API 라우터 (system.py, candidates.py, market.py 등 분리)
 ├── core/          # 공통 설정 (settings.py, domain.py)
 ├── services/      # 비즈니스 로직 (scoring.py, surge_scoring.py, batch.py)
 ├── db/            # 데이터베이스 (repository.py, postgres_repository.py)
 ├── collectors/    # 외부 API 연동 (Kiwoom, DART, KRX)
 └── scripts/       # 스크립트 실행
```
- **개선 방법**: `main.py`에서 `APIRouter`를 사용하여 엔드포인트들을 `api/` 폴더 내 여러 모듈로 쪼개고, `main.py`는 오직 앱 초기화와 라우터 등록만 담당하게 변경합니다.

### 🎯 2. 프론트엔드(Next.js) 컴포넌트 분리
`page.tsx`에 집중된 코드를 컴포넌트와 훅(Hook)으로 분리해야 합니다.

**권장 구조:**
```text
frontend/
 ├── app/
 │    └── page.tsx        # 레이아웃 렌더링 및 페이지 조합만 담당
 ├── components/          # UI 컴포넌트 분리
 │    ├── MarketRegimeBanner.tsx
 │    ├── CandidateList.tsx
 │    └── SignalDetail.tsx
 ├── hooks/               # 커스텀 훅 (API 호출 및 상태 관리)
 │    └── useDashboardData.ts
 └── types/               # 타입 정의 분리
      └── index.ts        # SystemStatus, Candidate, TradePlan 등
```

### 🎯 3. 스크립트 구조 관리
`app/scripts` 내부에는 순수 ETL(데이터 적재) 목적과 평가(배치 실행) 목적의 파일이 섞여 있습니다.
- 향후 스크립트가 늘어날 것을 대비하여, Python의 Click이나 Typer 라이브러리를 활용하여 단일 CLI 진입점(`cli.py`)을 만들어 관리하는 것을 권장합니다.

### 🎯 4. 컨테이너화 및 통합 배포 환경 구축
개발 및 운영 환경의 일관성을 위해 전체 프로젝트 컨테이너화가 필요합니다.
1. `backend.Dockerfile` 및 `frontend.Dockerfile` 작성
2. 최상단 `docker-compose.yml`을 작성하여 DB, Backend, Frontend를 명령어 한 번(`docker-compose up -d`)에 실행할 수 있도록 구성

## 3. 리팩토링 진행 권장 순서
1. **[최우선] 프론트엔드 리팩토링**: `page.tsx` 분리 작업. (가장 가시적이고 즉각적인 유지보수 효과 발생)
2. **[높음] 백엔드 라우터 분리**: `main.py` 다이어트 및 `app/api/` 패키지 구성.
3. **[보통] 인프라 개선**: 전체 도커화 및 로컬 실행 스크립트 통일화.
